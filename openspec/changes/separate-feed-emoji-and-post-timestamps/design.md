# Design

## Context

動機と変更範囲は`proposal.md`を参照する。

`lib/posts.ts`はMarkdown処理の末尾でTwemojiを適用する。Feed生成は同じ記事HTMLを再利用する。概要抽出はTwemojiより前に実行する。

記事は旧`date`で並ぶ。JSON-LDは公開日時と更新日時に同じ値を出す。Feedは記事の日時をライブラリの`date`へ渡す。Feed全体は生成時刻を更新日時にする。

`components/date.tsx`は`dt-published`を固定で出す。standard.site同期は旧`date`を`publishedAt`へ変換する。同期は本文の全文描画を実行しない。

既存正本には日付のみとオフセット付き日時が混在する。日時移行は値をそのまま保存する。例外として、承認したタイムゾーンなしの5記事は日本時間のISO日時へ明示化する。

## Goals / Non-Goals

**Goals:**

- 正本の日時をひとつの検証境界で扱う。
- 出力先の命名差を出力部分だけで吸収する。
- 共通Markdown処理を維持し、サイト表示だけにTwemojiを適用する。
- 固定入力で公開日時と更新日時の違いを検証する。

**Non-Goals:**

- Git履歴から最初の公開日時や最終編集時刻を復元しない。
- 記事編集時の日時自動更新機構を追加しない。
- RSS独自拡張、旧`date`互換、出力先ごとの正本を追加しない。
- 本文、URL、概要選択、Mermaidの描画方式を変更しない。
- 実装段階でも検証目的のライブATProto書き込みは実行しない。

## Decisions

### 1. 全記事と利用箇所を一括移行する

記事の必須型は`published: string`と`updated: string`にする。旧`date`は読まない。各記事の旧値を両フィールドへ転記する。承認した5記事は`YYYY-MM-DD HH:mm`を`YYYY-MM-DDTHH:mm:00+09:00`へ変換する。

読み込み境界は欠損と不正な日時を検出する。ページとstandard.site同期は同じ日時検証を使用する。検証結果は記事名とフィールド名を示す。

日付のみの値はUTC午前0時として解釈する。オフセット付き日時は瞬間を維持する。変換は実行環境のローカルタイムゾーンに依存しない。

一覧は`published`が表す瞬間の降順にする。単純な文字列比較は異なるオフセットを正しく比較しない。更新日時だけの変更は並び順に影響しない。

代替案の段階移行は、旧値と新値の優先順を恒久的に残す。サイトは全記事を管理するため、一括移行を選ぶ。

### 2. 絵文字変換は表示先の境界に置く

Markdownレンダラーは明示的な出力先`page`または`feed`を受け取る。共通のMarkdown処理と概要抽出は維持する。`page`だけが文字列化の直前にTwemojiを適用する。

既存ページ呼び出しの既定値は`page`にする。Feed生成は`feed`を明示する。Feed概要のフォールバックはUnicodeを保持したHTMLから生成する。

逆変換で画像を絵文字へ戻す案は採用しない。その方法は著者指定画像と生成画像の区別を必要とする。Markdownパイプラインの複製も採用しない。図やコードの処理差を増やすためである。

### 3. 可視表示と機械可読値を一致させる

記事ページは公開と更新の日時を常に表示する。両者が同じ場合も表示を省略しない。この方式は条件分岐を減らし、両mf2プロパティを維持する。

日時コンポーネントは公開と更新の種別を明示的に受け取る。記事の`h-entry`内で各`time`へ`dt-published`と`dt-updated`を付ける。既存一覧の日時表示は公開日時を使う。

OGは`article:published_time`と`article:modified_time`を出す。JSON-LDは`datePublished`と`dateModified`を出す。表示形式は既存の日本語日付表記を維持する。

### 4. Feedライブラリの命名差を生成部分で吸収する

現在の`feed`ライブラリは項目の`published`を公開日時として扱う。項目の`date`はAtomの更新日時とJSON Feedの`date_modified`を表す。

Feed生成は`published`へ正本の公開日時を渡す。`date`へ正本の更新日時を渡す。これによりRSSの`pubDate`も公開日時を使用する。正本にライブラリ都合の`date`を残さない。

Feed全体の`updated`は配信対象記事の更新日時の最大値にする。対象記事がない場合は固定値`1970-01-01T00:00:00.000Z`を使用する。空Feedでも生成時刻への暗黙の補完を避ける。

### 5. standard.siteは既存Lexiconへ直接対応させる

`buildStandardDocumentRecord`は`publishedAt`と`updatedAt`を設定する。両値は正本の日時をISO形式へ変換する。概要抽出とレコード比較は既存経路を維持する。

Lexiconでは`updatedAt`が任意だが、サイト正本では必須である。同期は省略分岐を設けない。

一次資料:

- https://standard.site/docs/lexicons/document
- https://microformats.org/wiki/h-entry

### 6. 回帰テストは記事から独立させる

Feedテストは既存の一時ディレクトリと解析済み出力の検証を拡張する。fixtureは絵文字、明示概要、本文抜粋、公開・更新が異なる日時を含む。

日時検証は日付のみ、オフセット付き、欠損、不正値を扱う。standard.siteテストはレコード生成関数を直接検証する。

HTMLテストは固定入力で両`time`とページメタデータを検証する。実記事は統合buildと移行結果の確認にだけ使う。テストは記事IDや文言を恒久的に固定しない。

## Risks / Trade-offs

- 既存`date`は最初の公開日時を保証しない → 合意した従来運用を維持し、推測による復元を実行しない。
- 不正値の検証は既存記事の問題を検出する → 移行前に全旧値を監査し、無断の値修正を避ける。
- Feed本文の修正は概要の絵文字にも影響する → 明示概要と既存抜粋を全形式で検証する。
- ライブ同期は外部レコードを書き換える → まず固定入力で検証し、公開同期は別途承認の対象にする。
- 完全buildは既存のMermaidブラウザ環境と同期設定を必要とする → 障害を日時・Feedテストと分けて報告する。

## Migration Plan

1. 実装者は全記事の旧日時と利用箇所を監査する。
2. 実装者は記事、型、読み込み、各出力、fixtureを同じ変更で移行する。
3. 実装者は旧値と新しい両値の一致を全記事で確認する。
4. 実装者は固定入力テスト、型検査、統合buildを実行する。
5. 実装者は変更範囲と出力結果をレビューへ提示する。

ロールバックは記事とコードをまとめて戻す。旧記事と新コードの混在を避ける。
